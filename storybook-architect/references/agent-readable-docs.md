# Agent-Readable: Same Artifacts, No Parallel Format

Agents hallucinate a `shadow` prop that doesn't exist, or reinvent a `Card` that already has three near-duplicates. Every one of those is a new entry for the next audit. The fix is a machine-readable contract the agent checks *before* generating — and Storybook generates it natively. **Do not hand-roll a parallel `llms-*.txt` export when the project has Storybook.** A hand-rolled export drifts the day someone forgets to regenerate it; the manifest is built from the same CSF the humans read.

All of the following verified against Storybook 10.6 docs, 2026-09-17.

## 1. Manifests

Storybook generates two, from static analysis of CSF and MDX plus prop extraction from component source:

| Manifest | Path (dev) | Contents |
|---|---|---|
| Components | `http://localhost:6006/manifests/components.json` | component names, descriptions, props, usage examples |
| Docs | `http://localhost:6006/manifests/docs.json` | MDX docs and standalone pages |

Same paths relative to the root of a built Storybook. Debugger UI: `/manifests/components.html`.

```ts
// .storybook/main.ts
export default {
  features: { componentsManifest: true },
  typescript: { reactDocgen: 'react-docgen-typescript' }, // fuller prop info than the default
};
```

Generated by the React frameworks, `@storybook/angular-vite`, and `@storybook/vue3-vite`. All stories and independent docs pages carry the `manifest` tag by default; `!manifest` removes one.

Source: https://storybook.js.org/docs/ai/manifests

## 2. MCP server

```bash
npx storybook add @storybook/addon-mcp
npx mcp-add --type http --url "http://localhost:6006/mcp" --scope project
```

Endpoint: `http://localhost:6006/mcp` (port varies). Tools exposed: `stories-changed`, `get-storybook-story-instructions`, `stories-preview`, `stories-find-by-component`, `review-create`, `docs-list`, `docs-show`, `docs-show-story`, `test-run`.

`test-run` is the part that matters most for maintenance: the agent can generate a story, run it, and fix its own failures — a closed validation loop rather than a one-shot guess.

Source: https://storybook.js.org/docs/ai/mcp/overview

## 3. The pointer in AGENTS.md / CLAUDE.md

Without it, agents keep guessing out of habit even with the manifest sitting right there. Storybook's recommended shape, with the toolset name replaced by yours:

```md
When working on UI components, always use the [your-project-sb-mcp] MCP tools to
access Storybook's component and documentation knowledge before answering or
taking any action. Query `docs-list` and `docs-show` first. Verify every property
against the manifest before using it — never assume a prop exists because it
sounds right for the framework. Run `test-run` to validate your work.
```

Add the project's own rules underneath: token grammar, the status enum, and that a new shared component needs a story before merge.

## 4. Curate what agents see

Storybook's own best practice: remove the `manifest` tag from stories demonstrating anti-patterns or deprecated components, so agents aren't trained on the mess you're documenting. In this skill that means `!manifest` on every audit page, every workshop story, and every `deprecated` component.

Also, from the same guidance:

- **One concept per story.** A `SizesAndVariants` story "demonstrates too many concepts at once, making it less clear and less useful as a reference for agents."
- **Describe the *why*.** Story descriptions should explain why you would use what's demonstrated, not restate what's on screen.
- **JSDoc the component and its props** — Storybook extracts it into the manifest automatically.
- **Put details in the MDX itself** rather than linking out to external sources.

Source: https://storybook.js.org/docs/ai/best-practices

## Fallback: static export

Only when Storybook's manifests aren't available (pre-10, an unsupported framework, or a published static reference with no dev server). Split by concern rather than dumping one file — an agent asking "what props does Button take" shouldn't have to load the whole token set:

- `llms-tokens.txt` — every token, value, and semantic purpose
- `llms-components.txt` — every component, real prop names and types, variants
- `llms-primitives.txt` — the low-level layout/text building blocks, if the system has them

This mirrors what Atlassian publishes alongside its human docs. Treat it as the compatibility path, not the target: it is a second artifact that must be regenerated, and the day it stops being regenerated it starts lying.

## Why this belongs in a maintenance skill

15 of 21 surveyed design systems ship an `llms-txt` affordance and 37 MCP-server affordances appear across the set, with consumer-facing affordances (131) outnumbering builder-facing ones (54) roughly 2.4:1 — the systems are being consumed by agents whether or not their maintainers planned for it.
Source: https://state-of-ai-in-design-systems.netlify.app (July 2026 snapshot)

If agents write a meaningful share of the UI in this repo, they regenerate decay as fast as you fix it. A manifest plus a validation loop is what makes the audit's numbers stay down.
